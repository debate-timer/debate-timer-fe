# 위키 유지보수 기준

이 문서는 정책·도메인 지식의 상태와 근거, 갱신 조건, 불일치 처리를 소유함. 문서 구조와 작성 양식은 [위키 안내](README.md), 형식과 소유권은 [문서 작성 컨벤션](../conventions/docs.md)을 따름.

## 지식의 상태와 근거

한 문서 안에서도 항목별로 다음 상태를 구분함. 문서 전체의 위치나 제목만으로 모든 내용을 확정 정책으로 취급하지 않음.

| 상태 | 의미와 필요한 근거 |
| --- | --- |
| 확정 정책 | 기존 승인 범위 또는 명시적으로 승인된 규칙임. 승인된 문서·결정·이슈·PR 등 확인 가능한 근거와 적용 범위를 연결함 |
| 구현에서 확인한 사실 | 코드·테스트·재현으로 관찰한 개념·관계·동작임. 근거와 확인한 범위·한계를 적으며 정책 승인으로 해석하지 않음 |
| 미확정 질문 | 의미나 의도를 확인해야 하는 항목임. 질문·확인한 사실·미확인 범위·다음 확인 방법을 적음 |

정책 승인, 구현 반영, 배포 완료는 별개임. 승인된 목표가 아직 구현되지 않았다면 `목표`로 표시하고 현재 확인한 상태와 구분함. 테스트가 존재한다는 사실과 해당 검증을 실제로 실행해 통과했다는 사실도 구분함.

기존 승인 범위에서 진행할 작업에 새 승인 단계를 추가하지 않음. 근거가 없거나 승인 범위가 불명확한 새 정책을 구현 관찰이나 다른 서비스의 관행만으로 확정하지 않음. 필요한 결정은 기존 작업 권한과 논의 절차를 따름.

## 언제 갱신하는가

| 변경·상황 | 처리 |
| --- | --- |
| 기능의 목적·용어·관계·상태의 의미가 바뀜 | 관련 기능 문서의 설명·정책·사용 예시를 확인하고 의미가 바뀐 부분을 갱신함 |
| 허용·거절·입력·표시 조건이나 사용자에게 보이는 결과가 바뀜 | 규칙을 소유한 절과 해당 조건을 사용하는 예시를 함께 확인함 |
| 중요한 선택의 이유·대안·한계가 바뀜 | 아래 기록 조건에 따라 결정 기록을 추가하고 현행 정책의 근거를 연결함 |
| 제품 의미를 유지하는 내부 리팩터링 또는 기존 계약을 복원하는 수정임 | 위키 갱신이 불필요할 수 있음. 참조 경로·식별자가 바뀌면 링크와 근거는 정리함 |
| 테스트 실행 결과·배포 상태·작업 진행만 바뀜 | PR·CI·배포 등 기존 기록에 남김. 위키에 실행 로그나 테스트 개수를 누적하지 않음 |

모든 코드 변경에 위키 수정을 요구하지 않음. 필요한 경우에도 전체 기능 문서를 재작성하지 않고 변경된 의미와 관련 참조를 갱신함.

## 문서·구현 사이의 불일치

기능 문서의 정책 절이 규칙을 소유하고 사용 예시는 해당 규칙이 적용되는 흐름을 설명함. 예시에서 새 규칙을 정의하거나 같은 정책·예시를 여러 위치에 복제하지 않음.

정책과 사용 예시, 구현과 문서 또는 소유 문서 사이에 차이가 있으면 관찰한 차이와 근거·영향 범위를 기록함. 기존 계약 위반인지, 의도한 변경의 문서 누락인지 확인함. 의도가 불명확하면 `판단 보류`와 확인 질문을 남기고 임의로 어느 쪽을 정책으로 확정하지 않음. 승인된 정책과 기존 기술 계약의 관계는 [문서 지도](../README.md#1-문서의-권위와-읽기-순서)를 따름.

## 결정 기록을 남기는 조건

앞으로의 구현·리뷰·제품 판단에 계속 영향을 주는 결정이면서 다음 조건 중 하나 이상에 해당하면 결정 기록을 남김. 코드 변경량이나 질문·승인의 개수로 판단하지 않음.

| 조건 | 판단 기준 |
| --- | --- |
| 중요한 의미·계약을 정함 | 용어·상태·권한·허용 조건·사용자 결과의 해석이 달라짐 |
| 여러 대안 중 하나를 선택함 | 선택 이유와 받아들인 한계를 모르면 나중에 잘못 바꿀 수 있음 |
| 기존 정책을 변경·폐기함 | 대체한 범위와 변경 이유를 추적할 필요가 있음 |
| 반복 오해·논쟁을 해소함 | 같은 질문을 반복하거나 폐기한 동작을 재도입할 가능성이 있음 |
| 영향·변경 비용이 큼 | 여러 기능·클라이언트·서버에 영향을 주거나 되돌리기 어려움 |

기존 정책대로 복원하는 버그 수정, 의미가 같은 리팩터링·파일 이동·오탈자 수정, 이미 명확한 정책의 재설명, 테스트·배포·진행 결과는 일반적으로 기능 문서나 PR·CI 기록으로 충분함. 그 과정에서 정책 자체를 새로 결정하면 해당 결정에는 위 조건을 적용함.

정책의 승인 근거는 상세 결정 기록의 작성 여부와 관계없이 보존함. 기록 조건에 해당하지 않는 단순 확인은 기능 문서에 승인일·승인 주체·근거·범위를 짧게 연결함. 모든 Q&A를 결정 기록으로 만들거나 근거가 없는 이유·대안을 LLM이 보충하지 않음.

## 결정 기록의 위치와 번호

- 기능별 기록은 `docs/wiki/decisions/{기능}.md`에 모음. 파일명은 기능 문서와 같은 소문자 영문·숫자·하이픈 이름을 사용함. 여러 기능의 공통 결정은 `shared.md`에 한 번만 기록하고 관련 기능에서 연결함.
- 결정 번호는 `{기능 접두어}-DEC-{일련번호}` 형식임. 접두어는 파일명의 영문을 대문자로 바꾸며, 번호는 해당 접두어 안에서 001부터 증가하는 최소 세 자리 숫자임. 공통 결정은 `SHARED-DEC-001` 형식임.
- 결정 기록을 분리하거나 다른 파일로 옮겨도 이미 부여한 번호를 유지함. 번호는 상태 변경·파일 이동에도 재사용하거나 재배정하지 않음. 같은 접두어의 최대 번호를 확인한 뒤 다음 번호를 사용하며 병합 전 중복을 확인함.
- 각 결정은 `### {결정 번호} — 짧은 제목` 형식의 제목으로 구분함. 기능 문서는 현행 정책을 소유하고 결정 번호가 있는 제목의 앵커로 승인 근거를 연결함.
- 새로운 기록은 독립적으로 바뀔 수 있는 결정 단위로 작성함. 같은 날 승인되었다는 이유만으로 서로 무관한 결정을 묶지 않음. 기존 묶음 기록은 근거와 번호를 보존함.

파일이 길어지면 문서 작성 컨벤션의 중복·책임·분량 기준을 적용함. 독립 분리가 필요하면 `decisions/{기능}/{번호}-{짧은-영문-제목}.md`로 옮기고 기존 기능별 기록 파일은 위치 안내로 정리함. 번호를 보존하고 모든 참조를 함께 갱신함.

## 결정 기록에 담는 내용

최소 필수 정보는 다음과 같음. 결정일·상태·근거는 한 줄로 묶을 수 있으며, 결정과 이유·정책 링크는 짧은 문장이나 표로 작성함.

| 필수 항목 | 기록 기준 |
| --- | --- |
| 번호·제목 | 결정의 고유 번호와 어떤 판단인지 드러나는 제목 |
| 결정일·상태 | 실제 승인·기각일을 `YYYY-MM-DD`로 기록함. 미결은 `미정`, 과거 날짜를 모르면 `미확인`으로 표시함. 상태는 `제안`·`승인`·`기각`·`대체` 중 하나임 |
| 근거 | 승인·기각 주체와 확인 가능한 문서·이슈·PR·사용자 지시를 짧게 식별함. 채팅 지시는 질문 주제와 답변 요지로 식별하고 링크가 있으면 연결함 |
| 결정·필요한 이유·정책 링크 | 선택한 내용과 나중의 판단에 필요한 이유, 관련 현행 정책의 위치를 남김. 단순 확인에 별도 이유가 제공되지 않았다면 결정과 링크로 충분함 |

다음 정보는 필요한 경우에만 추가함. 해당 없는 항목이나 빈 칸, 관례적인 `해당 없음`·`미확인` 설명을 채우지 않음.

| 조건부 항목 | 추가할 때 |
| --- | --- |
| 기록일 | 뒤늦게 복원한 기록 등 작성 시점 자체가 중요한 경우에만 결정일과 구분해 기록함 |
| 상황·적용 범위 | 결정 내용·이유·정책 링크만으로 이해하기 어려운 배경이나 오해하기 쉬운 적용 대상·예외가 있을 때 덧붙임 |
| 대안·한계·영향 | 실제 검토한 대안이나 중요한 한계·영향이 있을 때만 기록함. 판단에 중요한 미확인 사항은 명시하되 없던 검토를 만들지 않음 |
| 대체 관계 | 이전 결정을 대체하거나 이후 결정에 의해 대체되었을 때 번호·링크·대체 범위를 기록함 |

원본 대화·민감한 정보는 복제하지 않음. 승인·기각 근거는 의사결정의 증거이며 코드·테스트·배포 완료의 증거가 아님. 구현 차이와 미반영 상태는 기능 문서에 유지하고 작업별 실행 결과는 PR·CI에 기록함.

위 공통 규칙을 지켰다는 설명이나 의미 변화 없는 파일 이동 이력은 개별 결정에서 반복하지 않음.

## 결정의 변경과 질문 해소

승인·기각된 결정의 당시 상황과 판단을 새 결론으로 덮어쓰지 않음. 의미가 바뀌면 새 번호로 기록하고, 승인 후 현행 정책과 근거 링크를 갱신함. 이전 기록에는 `대체` 상태·대체 번호·대체 범위를 남기며 부분 대체이면 유효한 나머지 범위를 명시함. 새 제안이 아직 승인되지 않았다면 기존 확정 정책은 계속 적용함.

오탈자·깨진 링크의 수정, 상태·대체 관계 표시, 결정의 의미와 근거를 보존하는 중복 설명 축약은 같은 기록에서 정정할 수 있음. 기능 문서의 현행 규칙은 최신 상태로 갱신하며 과거 정책 전체를 누적하지 않음. LLM은 작업에 관련된 현행 정책을 먼저 읽고 이유·대체 관계가 필요할 때 결정 기록을 찾음. 모든 과거 결정을 매 작업마다 읽도록 강제하지 않음.

미확정 질문은 관련 기능 문서에 기록함. 해소되면 답변 근거와 반영 위치를 연결하고 질문 형태로 계속 누적하지 않음. 상세 기록 조건에 해당할 때만 결정 기록으로 분리하며 해결되지 않은 질문을 기대 결과나 확정 정책처럼 쓰지 않음.

## 작업과 리뷰에서의 적용

작업 시작 시 관련 기능 문서를 확인하고, 변경 후 위 표에 따라 영향을 판단함. 에이전트 실행 절차는 [AGENTS.md](../../AGENTS.md), 검토와 결과 기록은 [코드 리뷰 워크플로](../workflows/dt-fe-code-review.md), PR 준비는 [PR 생성 워크플로](../workflows/dt-fe-pull-request.md)가 소유함.

위키가 없는 기능은 기존 기술 계약을 따라 작업하고, 문서화 공백과 판단 근거를 작업 보고나 리뷰에 기록함. 위키 부재만으로 작업을 차단하거나 해당 기능의 전체 문서화를 강제하지 않음. 다만 불명확한 제품 동작이나 계약을 추측해 메우지 않음.

문서 검증은 링크·앵커·서술·관련 문서의 정합성을 확인함. 실제 제품 동작은 관련 테스트나 재현으로 별도 확인함. 사용 예시 작성이나 문서 검사 통과만으로 정책 승인·동작 검증·배포 완료를 주장하지 않음.
