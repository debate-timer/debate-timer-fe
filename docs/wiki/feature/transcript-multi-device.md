# 속기록 설계 - 멀티 디바이스 기반

## 목적과 제공 기능

사회자 기기 한 대의 마이크에 의존하던 Soniox 속기를, 실시간 공유에 참여한 청중 기기의 녹음까지 받아 턴마다 음성 품질이 가장 좋은 녹음 하나로 전사하는 기능임. 사회자 기기가 발언자와 멀어 소리가 작거나 잡음이 큰 경우에도 가까운 청중 기기의 녹음으로 속기록 품질을 높이는 것이 목적임.

- 대상: `MULTI_DEVICE_RECORDING` 피쳐 플래그를 받은 회원(사회자)과, 그 토론의 공유 링크로 입장해 녹음 참가에 동의한 청중임.
- 제공: 녹음 세션 시작·청중 참가, 턴별 녹음 업로드, 서버의 후보 선택·백그라운드 전사·S3 보관, 토론 종료 후 서버의 속기록 생성임.
- 경계: 기존 RPC·Soniox(V1) 속기는 그대로 유지함. 이 기능은 V2로 분리해 구현하며 전환·제거가 가능해야 함. 속기 시작·끄기와 로그아웃의 공통 수명은 [토론 메뉴와 진행 수명](debate-controls.md), 타이머 진행 규칙은 [타이머 진행](timer.md), 공유 통신 계약은 [실시간 통신](../../architecture/realtime.md)이 소유함.

**지식 상태:** 2026-11-12 계획 대화에서 사용자가 품질 판정·청중 권한·속기록 생성 방식을 선택하고 구현을 요청한 [결정](../decisions/transcript-multi-device.md#transcript-multi-device-dec-001--v2-분리와-턴별-후보-선택-방식)을 따르는 **목표** 설계임. BE는 [debate-timer-be PR #330](https://github.com/debate-timer/debate-timer-be/pull/330)에 구현했으나 병합·배포 전임. FE는 구현하지 않았음. 아래에서 BE 구현을 근거로 든 내용은 해당 PR에서 확인한 사실이며 운영 동작의 증거가 아님.

## 주요 개념과 관계

| 개념 | 의미 |
| --- | --- |
| 녹음 세션 | 사회자가 토론 하나에 대해 연 다기기 녹음 단위임. `sessionKey`로 식별함 |
| 참가 코드 | 청중 기기가 세션에 참가할 때 쓰는 비밀 값임. 세션 생성 응답에서만 받을 수 있고 서버는 해시만 보관함 |
| 기기·기기 토큰 | 세션에 참가한 사회자·청중 기기와 업로드 권한 토큰임. 토큰은 참가 응답에서만 받을 수 있음 |
| 턴 | 타이머가 한 번 실행된 발언 구간임. V1의 Soniox 구간과 같은 단위이며 자유토론 팀 전환도 새 턴임 |
| 턴 키 | 모든 기기가 같은 턴을 같은 값으로 가리키는 식별자임. `{타임박스 순서}-{그 구간을 시작한 공유 이벤트 version}` 형식임 |
| 후보 | 한 턴에 한 기기가 올린 녹음과 품질 지표임 |
| 수집 창 | 턴의 첫 후보가 도착한 뒤 다른 기기의 후보를 기다리는 시간임. 기본 20초임 |

### 세션 상태

| 상태 | 의미 | 전이 |
| --- | --- | --- |
| `RECORDING` | 기기들이 턴 녹음을 올리는 중임 | 세션 생성 시 시작함. 사회자 종료 시 `FINISHING` |
| `FINISHING` | 종료 후 늦은 업로드와 남은 턴 전사를 기다리는 중임 | 조건 충족 시 `COMPLETED` 또는 `FAILED` |
| `COMPLETED` | 속기록을 만들었음. `transcriptId`가 있음 | 종료 상태 |
| `FAILED` | 전사된 발언이 없거나 속기록을 만들지 못했음 | 종료 상태 |

### 턴 상태

턴은 수집 창이 닫힐 때 서버에 기록되며 `PROCESSING`(선택 후보 보관·전사 중) → `DONE` 또는 `FAILED`(모든 후보 전사 실패·고를 후보 없음)로 바뀜. 수집 중인 턴은 서버 메모리에만 있음.

## 기본 동작

1. 사회자가 속기 시작에서 다기기 녹음을 선택하면 FE가 `POST /api/v2/recordings`로 세션을 열고 참가 코드와 사회자 기기 토큰을 받음.
2. 사회자가 실시간 공유를 켜면 청중 화면에 녹음 참가 안내를 표시함. 참가 코드는 공유 링크·QR에 포함해 전달함.
3. 청중이 녹음 참가에 동의하면 FE가 `POST /api/v2/recordings/{sessionKey}/devices`로 기기 토큰을 받고 마이크를 준비함. 로그인은 필요 없음.
4. 사회자·청중 기기 모두 공유 이벤트에 맞춰 구간 녹음을 시작·종료하고, 구간이 끝나면 같은 턴 키로 `POST /api/v2/recordings/{sessionKey}/turns/{turnKey}`에 오디오와 품질 지표를 올림. 서버는 받아 두기만 하고 바로 202로 응답함.
5. 서버는 참가 기기가 모두 올리거나 수집 창이 지나면 턴을 마감하고, 품질 점수가 가장 높은 후보 하나를 S3 `stt-audio-v2/` 경로에 보관한 뒤 Soniox로 전사함.
6. 사회자가 토론을 끝내면 FE가 `POST /api/v2/recordings/{sessionKey}/finish`를 호출함. 서버는 수집 창 동안 늦은 업로드를 더 받고, 남은 턴 처리가 끝나면 전사된 턴으로 속기록을 만들고 기존 다듬기·분석을 이어감.
7. 사회자 FE는 `GET /api/v2/recordings/{sessionKey}`를 폴링해 `COMPLETED`가 되면 `transcriptId`로 기존 속기록 화면으로 이동함.

V1과 달리 FE가 구간별 전사 결과를 모아 `POST /api/transcripts/{tableId}`로 제출하지 않음. 요청·응답 형식은 BE Swagger의 `Recording V2 API` 태그를 따름.

## 조건별 정책과 예외

### 녹음 세션과 권한

| 항목 | 내용 |
| --- | --- |
| 지식 상태 | 목표(결정 승인)·BE 구현에서 확인한 사실 |
| 대상과 조건 | 세션 생성·조회·종료·사회자 재참가는 플래그가 있는 테이블 소유 회원만 호출함. 청중 참가는 참가 코드, 업로드는 `X-Recording-Device` 기기 토큰으로 확인함 |
| 동작과 결과 | 사회자 기기를 포함해 세션당 최대 8대가 참가함. 초과하면 `409 RECORDING_DEVICE_LIMIT_EXCEEDED`임. 참가 코드가 틀리면 `403`, 끝난 세션이면 `409 RECORDING_SESSION_CLOSED`임 |
| 예외와 복구 | 사회자 기기가 새로고침·서버 재시작으로 토큰을 잃으면 `POST /{sessionKey}/host-device`로 사회자 기기로 다시 참가함. 청중은 참가 코드로 다시 참가함. 재참가는 사회자·청중 모두 새 기기를 추가하며 기존 기기를 교체·회수하지 않음. 토큰을 잃은 기기도 정원에 남으므로 정원이 찬 세션에서는 사회자 재참가도 `409 RECORDING_DEVICE_LIMIT_EXCEEDED`임. 서버 재시작으로 메모리의 기기 목록을 잃으면 정원도 비워짐 |
| 근거와 적용 범위 | BE `RecordingServiceV2`·`RecordingSessionRegistryV2`·`RecordingControllerV2`와 테스트임. 재참가의 정원 처리는 구현에서 확인한 사실이며 승인한 정책이 아님([미확정 질문](#결정-근거와-미확정-질문)). 기능이 꺼져 있으면(`recording-v2.enabled=false`, 기본값) V2 API는 `404 RECORDING_V2_DISABLED`임 |

### 턴 키와 시간 기준

| 항목 | 내용 |
| --- | --- |
| 지식 상태 | 목표. FE 생성 규칙은 미구현임 |
| 대상과 조건 | 모든 참가 기기가 같은 구간에 같은 턴 키를 써야 같은 턴의 후보로 모임 |
| 동작과 결과 | 턴 키는 `{timeBoxIndex}-{version}`이며 `version`은 그 구간을 시작한 공유 이벤트의 값임. 영문·숫자·`_`·`-` 64자 이하가 아니면 `400 INVALID_RECORDING_TURN`임. `startedAtEpochMs`는 공유 이벤트의 `serverTime`으로 추정한 서버 시계 기준 녹음 시작 시각임 |
| 예외와 복구 | 서버는 턴 키만으로 후보를 묶음. 구간 시작 이벤트를 놓친 기기가 다른 턴 키로 올리면 같은 발언이 별도 턴으로 전사되어 속기록에 중복될 수 있음. 중도 입장·재연결 청중은 사회자의 동기화 응답을 받는데, 사회자는 발행마다 새 `version`을 쓰므로 이 응답으로는 구간 시작 `version`을 알 수 없음([미확정 질문](#결정-근거와-미확정-질문)). 서버는 전사된 턴 중 가장 먼저 시작한 턴을 0으로 두고 각 턴의 문장 시간을 토론 경과 시간으로 맞춤. 기기 시계 추정 오차만큼 턴 사이 간격이 어긋날 수 있음 |
| 근거와 적용 범위 | BE `RecordingSessionRegistryV2`·`TranscriptAssemblerV2`, FE [사회자 소켓](../../../src/hooks/sockets/useChairmanSocket.ts)의 발행 `version` 계산과 [TimerPage](../../../src/page/TimerPage/TimerPage.tsx)의 동기화 응답임. `version`·`serverTime`의 의미는 [실시간 통신](../../architecture/realtime.md)과 `src/apis/sockets/type.ts`를 따름 |

### 후보 선택

| 항목 | 내용 |
| --- | --- |
| 지식 상태 | 목표(결정 승인)·BE 구현에서 확인한 사실 |
| 대상과 조건 | 수집 창이 닫힌 턴의 모든 후보임 |
| 동작과 결과 | 크기 대비 길이가 압축 오디오 비트레이트(4~512kbps)를 벗어나는 후보는 제외함. 지표가 모두 있고 범위가 맞는 후보를 먼저 두고, SNR·적정 음량(-30~-12dBFS)·발화 비율·클리핑 감점·같은 턴 최장 녹음 대비 길이로 점수를 매김. 동점이면 사회자 기기, 먼저 도착한 후보 순임 |
| 예외와 복구 | 1순위 후보 전사가 실패하면 다음 후보로 전사함. 모두 실패하거나 고를 후보가 없으면 턴을 `FAILED`로 기록하고 속기록에서 빠짐 |
| 근거와 적용 범위 | BE `AudioQualityScorerV2`·`TurnProcessorV2`와 테스트임. 지표는 기기가 보낸 값이라 조작될 수 있으며 범위·크기 검증과 기기 수 제한으로만 완화함 |

품질 지표는 Web Audio로 녹음하며 계산함.

| 지표 | 의미 |
| --- | --- |
| `rmsDb` | 평균 음량(dBFS, 0 이하) |
| `peakDb` | 최대 순간 음량(dBFS, 0 이하, `rmsDb` 이상) |
| `clippingRatio` | 최대 진폭에 닿은 샘플 비율(0~1) |
| `silenceRatio` | 무음 구간 비율(0~1) |
| `snrDb` | 발화 구간 음량과 잡음 바닥의 차이(dB) |

### 업로드 마감

| 항목 | 내용 |
| --- | --- |
| 지식 상태 | 목표(결정 승인)·BE 구현에서 확인한 사실 |
| 대상과 조건 | 턴 업로드와 사회자 종료임 |
| 동작과 결과 | 마감된 턴에 올리면 `409 RECORDING_TURN_CLOSED`임. 같은 기기가 마감 전에 다시 올리면 새 녹음으로 바꿈. 종료 후 수집 창 동안은 늦은 업로드를 받고, 이후에는 `409 RECORDING_SESSION_CLOSED`임 |
| 예외와 복구 | 서버 임시 저장 용량이 가득 차면 `429 RECORDING_BUSY`임. 종료 후 10분이 지나면 처리가 끝난 턴만으로 속기록을 만듦 |
| 근거와 적용 범위 | BE `RecordingSessionRegistryV2`·`RecordingFinalizerV2`와 테스트임 |

### 서버 상태 유실

**구현에서 확인한 사실:** 참가 기기 목록과 수집 중인 턴은 서버 메모리에만 있음. 서버 재시작·무중단 배포 중에는 수집 중인 턴을 잃음. 이미 마감된 턴은 DB에 남음. 기존 실시간 공유와 같은 단일 인스턴스 가정임.

사회자가 종료하지 않고 떠난 세션은 속기록을 만들지 않으며 12시간 뒤 서버 메모리와 임시 파일만 정리함.

## 대표 사용 흐름·예시

**목표 흐름:** 사회자가 교실 앞 노트북으로 타이머를 진행하고 청중 3명이 휴대폰으로 공유 링크에 입장해 녹음 참가에 동의함. 찬성 1번 입론 구간이 끝나면 네 기기가 같은 턴 키로 녹음을 올림. 발언자 옆 청중 휴대폰의 SNR이 가장 높아 그 녹음만 전사됨. 상태 조회의 해당 턴에는 후보 수 4와 선택된 기기 ID가 표시됨. 사회자가 토론을 끝내고 약 20초 뒤부터 남은 전사가 끝나면 속기록이 만들어짐.

청중이 없거나 아무도 참가하지 않으면 사회자 기기만 후보가 되어 V1 Soniox와 같은 결과가 됨. 정책은 [후보 선택](#후보-선택)과 [업로드 마감](#업로드-마감)을 따름.

## 결정 근거와 미확정 질문

결정 이유·검토한 대안은 [TRANSCRIPT-MULTI-DEVICE-DEC-001](../decisions/transcript-multi-device.md#transcript-multi-device-dec-001--v2-분리와-턴별-후보-선택-방식)에 있음.

| 질문 | 확인한 사실 | 다음 확인 방법 |
| --- | --- | --- |
| 청중 녹음 동의 문구와 절차는 무엇인가 | 사회자 속기는 녹음 동의를 거침. 청중 기기 녹음의 동의·고지 정책은 없음 | 기획·법무 검토 후 문구와 거절 시 동작을 결정함 |
| 진행 중 참가·재연결 기기는 구간 시작 `version`을 어떻게 얻는가 | 동기화 응답은 새 `version`을 쓰고, BE 참가·상태 응답에도 현재 구간 정보가 없음. 실시간 통신은 놓친 이벤트를 다시 보내지 않음 | 동기화 응답에 구간 시작 `version`을 싣는 안, 중도 입장 기기는 다음 구간부터 녹음하는 안 등을 검토해 [턴 키와 시간 기준](#턴-키와-시간-기준)에 반영함 |
| 토큰을 잃은 기기의 정원을 회수할 것인가 | 재참가는 새 기기를 추가하고 기존 기기는 정원과 수집 창의 제출 대상에 남음. 남은 기기 때문에 턴은 전원 제출 조기 마감 없이 수집 창 시간까지 기다림 | 사회자 재참가 시 기존 사회자 기기 교체, 기기 만료·해제 API 등을 결정하고 FE의 정원 초과 안내를 정함 |
| 공유를 켜지 않은 토론에서도 V2를 쓰는가 | 청중은 공유 이벤트로 턴 경계를 알므로 공유가 없으면 사회자 기기만 참가함 | 사회자 속기 시작 화면에서 V1·V2 선택 조건을 결정함 |
| 다기기 녹음의 진입점과 V1 모드와의 관계는 무엇인가 | 속기 시작은 RPC/Soniox를 선택하고 최초 성공 후 모드를 잠금 | [토론 메뉴](debate-controls.md) 정책 개정 여부를 결정함 |
| 청중 화면에 녹음 중·업로드 실패를 어떻게 알리는가 | BE는 업로드 실패를 오류 코드로만 응답함 | 청중 UI 설계에서 결정함 |
| 일시정지 후 재개를 같은 턴으로 볼 것인가 | 현재 턴 키는 구간을 시작한 이벤트마다 달라 재개는 새 턴임 | V1 구간 분할과 같게 유지할지 확인함 |
| 서버가 어떤 기기를 선택했는지 사회자에게 보여줄 것인가 | 상태 조회는 턴별 선택 기기 ID와 후보 수를 제공함 | 사회자 화면 노출 여부를 결정함 |

## 검증 근거와 한계

- BE: PR #330의 점수기·수집 창·레지스트리·처리기·서비스·속기록 생성·컨트롤러·REST Docs 테스트가 있음. 실행 결과는 PR·CI에 남김.
